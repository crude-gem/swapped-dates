# swapped-dates

## How to Compile and Run

Run `make` to build.  `make run` to run the program.
Open the `Makefile` to configure things, like which compiler to use.

All make targets:
- `all`
- `clean`
- `run`
- `debug`
- `release`

By default, `make` will execute the `all` target, which, confusingly, only
executes the `release` target.  Too lazy to change it right now.  (TODO...)

## Intro

I made this project because I was curious about (what I call) "swapped dates."

## Explanation

It's better explained through an example.  Take March 7th and transform it into
the American calendar date format: 3/7.  The swapped version is 7/3, or July
3rd.  What is the distance between these two dates?  The answer is 118 days.
Is there a pattern between all 144 (12x12) combinations of these so-called
swapped dates?  Maybe.  I made a simple project that calculates it and displays
it in a semi-pleasant table.  Take a look and see if you spot any interesting
patterns.

Note that the distances between dates are strictly within a year.  So, the
distance between January 12th and December 1st (1/12 and 12/1) is 323 days, not
42 days.

## Future Features

In the future, I want to add "roundabout distance" calculation to these calendar
dates, where the shortest distance is always calculated between two dates, even
across years (so that January 12th and December 1st are 42 days apart). I also
want to implement color-coding, like a heat map of some sort. With color-coding,
more patterns may be visible.

## Why in C?

Why in C?!  For practice.  It would have been a lot faster to develop this
program in Python, but I appreciate C's ruggedness.  Besides, I needed an excuse
to actually start developing my own utility libraries, like memory arenas.
I did not use the arena much (at all) in this program, but I created the API
spontaneously.  I plan to make another code repository that holds all my utility
libraries.  I'll put my arena code in there, along with some other useful
functions.

# Notes

## How I Programmed It

I used Neovim and the `clangd` LSP to program this project.  Additionally,
I used the [`bear`](https://github.com/rizsotto/Bear) utility to generate the
`compile_commands.json` file that `clangd` reads for include directories.

## AI Usage?

AI (usually Claude) was used to help answer questions concerning API design,
weird behavior happening (not bugs), and the C programming language (such as how
exactly data is passed to and returned from functions; it's been some time since
I've used C).  At the end of the day, I still went with my own API design, since
the crap AI was giving me was just that.  Crap.

I did not use Claude Code.  Everything was hand-typed, and I invoked the
compiler by hand.  All the algorithms were invented by me.

The one thing that's AI-generated in the true sense of the word is the
`Makefile`.  I know a basic level of Make, but I wanted more complicated
compiler automation with a defined directory structure.  Since I cared more
about C programming than setting up my build system, I told Claude to write the
`Makefile` for me.  I inspected it, of course, and it seems to work fine.  This
is the only file I did not write myself (and is not generated by a simpler
computer program like a compiler or `bear` or `git`).
